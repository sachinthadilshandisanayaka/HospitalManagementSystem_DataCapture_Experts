DCE/LK/ST3 - Java Coding Assessment
Clinic Appointment & Notification API (Spring Boot + MongoDB)
1. Objective
Build a RESTful API for a clinic to manage Patients, Practitioners (Doctors), Appointments, and
Notifications triggered on appointment events.
The solution must demonstrate Spring Boot REST API development, MongoDB persistence, OOP
concepts, and at least one well-known design pattern.
2. Tech Requirements (Must Use)
• Java 17+
• Spring Boot 3.x
• MongoDB (local or container)
• Spring Web
• Spring Data MongoDB
• Bean Validation (Jakarta Validation)
• Maven or Gradle
• (Optional) Lombok
3. Business Domain & Entities
3.1 OOP Requirement (Mandatory)
Model people in an OOP way using either:
• Inheritance: Person → Patient, Practitioner
• OR Composition: Patient has Person Details, Practitioner has Person Details
Demonstrate polymorphism in a meaningful way (e.g., notification channel behavior or mapping
logic).
3.2 Entities (Minimum Fields)
Patient
• id (Mongo ObjectId as String)
• fullName (required, min 3 chars)
• nationalId (required, unique)
• dateOfBirth (required)
• contact: email (optional, valid), phone (optional)
Practitioner
• id
• fullName (required)

4. Core Rules
4.1 Appointment Conflict Rule (Mandatory)
A practitioner cannot have overlapping appointments. Overlap definition:
(newStart < existingEnd) AND (newEnd > existingStart)
(for the same practitioner, where existing status is BOOKED)
4.2 Status Rules
• You can cancel an appointment only if it is currently BOOKED.
• (Optional) Completed appointments cannot be edited — if implemented, document in README.
5. API Requirements (Mandatory Endpoints)
5.1 Patients
1. 2. 3. POST /api/patients — Create Patient
GET /api/patients/{id} — Get Patient by Id
GET /api/patients?nationalId=... OR ?name=... — Search Patients
5.2 Practitioners
4. 5. 6. POST /api/practitioners — Create Practitioner
GET /api/practitioners/{id} — Get Practitioner by Id
GET /api/practitioners — List Practitioners
5.3 Appointments

6. Design Pattern Requirement
Implement at least ONE well-known design pattern and explain it in the README.
• Option A — Strategy Pattern (recommended): NotificationStrategy interface with
Email/SMS/Console implementations.
• Option B — Factory Pattern: NotificationStrategyFactory returns strategy based on channel.
• Best: Strategy + Factory together (still simple, shows maturity).
7. Notification Behavior
When an appointment is:
• Created → send 'Appointment booked…'
• Cancelled → send 'Appointment cancelled…'
• Updated (notes) → send 'Appointment updated…'
Notification may be console logging but must be implemented using the selected pattern.
8. Validation & Error Handling
8.1 Validation
• Use Bean Validation annotations for required fields and formats.
• Validate start/end time logic (custom validator or service-layer check).
8.2 Error Response Format
Return consistent error responses like:
{
"timestamp": "2026-04-24T10:00:00Z",
"status": 400,
"error": "Bad Request",
"message": "Validation failed",
"details": [
"fullName must be at least 3 characters",
"endTime must be after startTime"
],
"path": "/api/appointments"
}
Handle at least: 400 validation errors, 404 not found, 409 conflicts (appointment overlap).
